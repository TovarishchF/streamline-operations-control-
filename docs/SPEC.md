# SPEC.md — функциональная спецификация системы SOC

Документ уточняет оригинал ТЗ (`docs/ТЗ_SOC.docx`). Нумерация разделов здесь **своя**;
привязка к пунктам оригинала указана в каждом блоке как `[ТЗ x.y.z]`.

Область документа — функциональность и интерфейс. Серверная часть описана в `BACKEND.md`,
внешние подключения — в `INTEGRATIONS.md`, мобильный клиент — в `MOBILE.md`,
испытания — в `TESTING.md`, развёртывание — в `INFRA.md`.

---

## 1. Границы реализации

Система реализуется полностью: PostgreSQL, серверное приложение, веб-клиент, мобильные
клиенты, фоновые задачи, отчётность. Единственная граница проходит по внешним системам,
доступ к которым зависит от заказчика или не существует публично.

### 1.1 Режимы внешних подключений

Каждое внешнее подключение реализуется как **адаптер** с двумя режимами:

- `live` — работа с настоящей внешней системой;
- `stub` — детерминированные искусственные данные того же формата.

Режим задаётся переменной окружения на каждое подключение отдельно
(`INTEGRATION_<CODE>_MODE`). Доменный код разницы не видит: он работает с интерфейсом
адаптера, а не с провайдером. Переход `stub → live` — замена реализации и заполнение
учётных данных, без правок бизнес-логики.

Полный реестр подключений, что именно нужно запросить у заказчика по каждому и как ведёт
себя заглушка — `docs/INTEGRATIONS.md`. Этот файл является основным документом
для согласования с заказчиком.

### 1.2 Демонстрационный стенд

Для показа заказчику разворачивается стенд с наполненной базой (`DEMO_DATA=true`) и всеми
подключениями в режиме `stub`. Стенд — это полноценная система, а не макет: те же сервер,
база, расчёты и API, отличаются только источники внешних данных.

Признак демонстрационного режима виден в интерфейсе и проставляется на всех выгружаемых
документах (§ 8.6). В боевом режиме (`DEMO_DATA=false`, подключения в `live`) маркировка
не выводится.

### 1.3 Вне объёма работ

- Приобретение платных источников данных и заключение договоров с провайдерами —
  зона ответственности заказчика (см. `INTEGRATIONS.md § 6`).
- Сертификация в IATA SIS/ISS.
- Юридическая экспертиза налоговых расчётов: справочник ставок реализуется, соответствие
  требованиям законодательства подтверждается бухгалтером заказчика.
- Опытная эксплуатация на реальных рейсах (этап 7 ТЗ) — выполняется совместно
  с заказчиком, силами исполнителя не закрывается.

## 2. Роли и доступ `[ТЗ 4.3]`

### 2.1 Вход в систему

Экран `/login`. Аутентификация настоящая всегда: пароль проверяется, второй фактор —
TOTP через приложение-аутентификатор, блокировка после 5 неудачных попыток (ADR-013).

Упрощённый вход (любой пароль, код `000000`, переключатель «Войти как») существует
**только** при `DEMO_DATA=true` и `DEBUG=true`, реализован отдельным бэкендом
аутентификации и физически не подключается в боевой сборке: обнаружение его
в настройках отказывает в запуске. Оставленный в бою обход входа — это уязвимость,
а не удобство демонстрации.

### 2.3 Реализация

Права описываются декларативно одной картой `role → (permission → boolean)`, общей для
сервера и клиентов: на сервере — источник истины, на клиент она приходит вместе с профилем
пользователя.

На клиенте компонент `<Can permission="flight.edit">` скрывает недоступные элементы,
хук `usePermission` используется в обработчиках. **Проверка на сервере обязательна
в каждом эндпоинте** и возвращает 403 при отсутствии права. Скрытие элемента в интерфейсе
без серверной проверки не засчитывается: это не разграничение доступа, а его видимость.

Для ролей «Клиент» и «Поставщик» дополнительно применяется фильтрация выборки
по арендатору (`BACKEND.md § 3.7`) с обязательным тестом на протечку данных для каждого
эндпоинта, доступного порталам.

## 4. Модуль «Суточный план полётов» `[ТЗ 3.1]`

### 4.1 Планшет Gantt `[ТЗ 3.1.1]`

- Строки — борта ВС, сгруппированные по типу; в конце — группа «Без борта» для рейсов,
  где борт ещё не назначен.
- Полоса рейса: `рейс № · ICAO вылета → ICAO прилёта`, цвет = статус.
- Масштабы: сутки / трое суток / неделя. Кнопка «Сейчас» возвращает к текущему моменту.
- Вертикальная линия текущего времени, обновляется по `useClock`.
- Перетаскивание полосы меняет время вылета, растягивание — продолжительность,
  перенос на другую строку — смену борта. Каждое такое действие проходит через тот же
  сценарий, что и форма редактирования: проверка конфликтов → подтверждение → аудит →
  постановка уведомлений в «Исходящие» `[ТЗ 3.1.3]`.
- Подсветка конфликтов: пересечение рейсов одного борта, нарушение минимального времени
  между рейсами (`turnaroundMin` у типа ВС), рейс на борту со статусом AOG или
  «на техобслуживании». Конфликт не блокирует сохранение, но требует подтверждения
  с указанием причины, и причина пишется в аудит.

### 4.2 Табличный вид `[ТЗ 3.1.1]`

Плотная таблица с фильтрами: период, борт, тип ВС, клиент, статус, тип рейса, аэропорт
(вылета или прилёта), «есть неподтверждённые услуги», «маржа ниже N %».
Сохранение набора фильтров как именованного пресета (в localforage).
Колонки настраиваются и запоминаются. Сортировка по любой колонке.
Массовые действия: изменить статус, назначить поставщика по категории, выгрузить в XLSX.

### 4.3 Часы и автопереходы

Единый источник времени — `useClock()`, тик 1 с, в сторе одно значение `nowUtc`.
Доменный код получает время параметром, `new Date()` внутри домена запрещён.

В интерфейсе есть панель управления демонстрацией: ускорение времени ×1 / ×60 / ×600
и кнопка «Перемотать на N часов». Без неё автопереходы невозможно показать за встречу.

Смещение хранится на **сервере** в `core.Settings` и применяется внутри `core.clock.now()`
(ADR-014): автопереходы выполняет Celery по серверным часам, поэтому клиентская перемотка
сдвинула бы только линию «сейчас» и не показала бы ничего. При `DEMO_DATA=false` изменение
запрещено на уровне сервиса. Записи аудита, сделанные при включённом смещении, помечаются
`clockShifted` и не выдаются за реальную хронологию.

Автопереходы:
- `ready_for_departure → in_flight` при `nowUtc >= std`;
- `in_flight → arrived` при `nowUtc >= sta`. Переход `arrived → completed` автоматическим
  **не является**: он требует закрытых заявок и выставленного счёта (ADR-009);
- нарушение SLA заявки: если поставщик не подтвердил за `slaConfirmMin` — флаг
  `slaBreached`, уведомление диспетчеру, запись в реестр нарушений.

### 4.4 Жизненный цикл и переходы `[ТЗ 3.1.2]`

Реализуется на XState, определение — `docs/DOMAIN.md § 5`. В UI: панель статуса в шапке
карточки рейса, доступные переходы — кнопки, недоступные — скрыты; при заблокированном
переходе рядом список невыполненных условий («не подтверждены 3 услуги», «нет пермита
на пролёт»). Переход в «Отменён» и «AOG» требует выбора причины из справочника и
комментария, оба попадают в уведомления.

### 4.5 Шаблоны регулярных рейсов `[ТЗ 3.1.1]`

Шаблон хранит маршрут, тип ВС, клиента, набор услуг по умолчанию и время вылета в
локальной зоне аэропорта вылета. Генерация серии: период, дни недели, исключения.
Предпросмотр списка будущих рейсов до создания. Изменение шаблона не трогает уже
созданные рейсы (и это пишется подсказкой в форме).

### 4.6 Карточка рейса `[ТЗ 3.1.4]`

Шапка: номер, клиент, борт, маршрут, время вылета/прилёта в UTC и локальном, статус,
сводка маржи (сумма и процент, цвет по порогу из настроек).
Вкладки — см. § 3. Правая панель «Контекст» (сворачиваемая): ближайшие дедлайны,
непрочитанные события по рейсу, быстрые действия.

## 5. Модуль «Управление услугами» `[ТЗ 3.2]`

### 5.1 Каталог `[ТЗ 3.2.1]`

Дерево категорий строго по ТЗ: топливообеспечение, наземное обслуживание, кейтеринг,
транспорт, разрешительные документы, противообледенительная обработка.
Позиция каталога: код, наименование ru/en, категория, единица измерения, признак
«требует привязки к погоде», признак «требует лидтайма», лидтайм в часах, набор
обязательных атрибутов заказа (например, для топлива — марка Jet A-1/Avgas и объём).

### 5.2 Заказ услуги `[ТЗ 3.2.2]`

Мастер в карточке рейса: выбор категории → услуги → плеча (вылет/прилёт/оба) →
атрибутов → поставщика.

Автоматические проверки выполняются **до** отправки и показываются списком с иконками:
1. услуга доступна в аэропорту плеча (есть хотя бы один поставщик с ценой);
2. у поставщика действующий контракт на дату оказания услуги;
3. цена актуальна на дату оказания (есть действующий `VendorPrice`);
4. лидтайм соблюдён (до вылета больше `leadTimeH`), иначе предупреждение;
5. для противообледенительной обработки — погодные условия из фикстуры допускают
   отказ от услуги, тогда показывается подсказка, а не запрет.

Провал проверок 1–3 блокирует отправку. Провал 4–5 требует подтверждения с причиной.

«Автоматическое резервирование» из ТЗ реализуется так: заявка переходит в статус
«Заказана», в «Исходящие» кладётся сформированное письмо поставщику, в портале
поставщика появляется задача. Часть заявок в демо-режиме автоподтверждается по таймеру
(настраивается на `/admin/demo-data`), чтобы показать поток без ручных кликов.

### 5.3 Контроль исполнения `[ТЗ 3.2.3]`

Статусы: Заказана → Подтверждена → В процессе → Выполнена (плюс Отклонена и Отменена).
Фиксируются `orderedAt`, `confirmedAt`, `startedAt`, `completedAt` — системные,
и `actualStartAt`, `actualEndAt` — фактическое время оказания, вводится вручную
и именно оно идёт в биллинг `[ТЗ 3.2.3]`.

Отклонение поставщиком открывает форму переназначения с подсказкой следующего
подходящего поставщика по правилам § 6.2.

Документы: загрузка файла (drag&drop) → S3-совместимое хранилище по подписанной
ссылке (ADR-007) → превью в карточке услуги,
тип документа из справочника (акт, квитанция, накладная, счёт), обязательность типа
«акт» для перехода в «Выполнена» — настраивается по категории.

## 6. Модуль «Контрагенты и третьи лица» `[ТЗ 3.3]`

### 6.1 Реестр поставщиков `[ТЗ 3.3.1]`

Профиль: реквизиты и контакты (несколько контактных лиц с ролями), специализации,
география покрытия (список ICAO и/или регионов), условия сотрудничества (валюта,
отсрочка в днях, порог предоплаты), сертификаты и допуски с датами действия
(IATA, ADR и прочие — справочник расширяемый), рейтинг, вложения.

Рейтинг — **вычисляемый**, не поле ввода. Формула в `DOMAIN.md § 7.4`: взвешенная
сумма доли подтверждений в срок, доли выполнений без нарушения SLA, доли услуг без
расхождений в сверке и ручной оценки качества (0–5), выставляемой диспетчером.
На экране — разложение рейтинга на составляющие, иначе цифра выглядит выдуманной.

### 6.2 Назначение поставщика `[ТЗ 3.3.2]`

Ручной выбор из отфильтрованного списка либо автоматический по одному из режимов:
по цене, по рейтингу, по географической близости (наличие базы в аэропорту, затем
расстояние до аэропорта по координатам), либо по взвешенной комбинации с настраиваемыми
весами. Перед применением показывается таблица сравнения кандидатов с итоговым баллом —
решение должно быть объяснимым.

При назначении в заявку **фиксируется закупочная цена** (снимок `VendorPrice` на момент
назначения, а не ссылка), чтобы последующее изменение прайса не меняло историю.

### 6.3 Контракты `[ТЗ 3.3.3]`

Реестр договоров: номер, поставщик, период действия, валюта, условия оплаты, файлы.
Уведомления об истечении за 30, 15 и 7 дней формируются планировщиком на `useClock`
и попадают во внутренние уведомления и в «Исходящие». Повторно одно и то же уведомление
не создаётся (ключ идемпотентности `contractId + порог`).
На `/contracts` — светофор: действует / истекает / истёк, с фильтром по умолчанию
«требуют внимания».

## 7. Модуль «Финансовые условия и взаиморасчёты» `[ТЗ 3.4]`

Самый ответственный модуль. Все формулы — в `DOMAIN.md § 7`, здесь только интерфейс и правила.

### 7.1 Тарифы и условия клиента `[ТЗ 3.4.1]`

Карточка клиента: валюта расчётов (USD/EUR/RUB), схема оплаты (предоплата / постоплата /
отсрочка N дней), скидки и наценки — процент или фиксированная сумма, с областью действия
(на всё, на категорию, на конкретную услугу, на аэропорт) и периодом действия.

Способ ценообразования на каждую позицию тарифа:
- `cost_plus` — закупочная цена + наценка %;
- `fixed` — фиксированная цена продажи независимо от закупки;
- `pass_through` — по закупочной цене без наценки (для сборов и пермитов).

Разрешение конфликтов правил — по специфичности: услуга → категория → всё;
при равной специфичности выигрывает правило с более поздним `validFrom`.
На экране тарифа — калькулятор-песочница: выбрать услугу и аэропорт, увидеть,
какое правило сработало и почему.

### 7.2 Котировка и счёт `[ТЗ 3.4.1]`

Котировка (Quote) формируется из планируемых услуг рейса до вылета, счёт (Invoice) —
из фактически оказанных после завершения. Оба документа:
- нумерация по маске из настроек (`SOC-Q-{YYYY}-{NNNN}`, `SOC-I-{YYYY}-{NNNN}`),
  счётчик — таблица `billing.DocumentCounter` с `select_for_update`, дыр не допускается;
- после выставления документ **неизменяем**: правки только через аннулирование
  и выпуск нового с ссылкой на предыдущий;
- курс валюты фиксируется на дату документа и сохраняется в самом документе;
- строки: услуга, аэропорт, количество, цена, сумма, ставка НДС, сумма НДС;
- итоги: подытог, сборы и комиссии, скидки, НДС, итого;
- экспорт в PDF и XLSX с водяным знаком DEMO;
- при формировании счёта — явное сопоставление «план ↔ факт» с подсветкой отличий,
  чтобы было видно, за счёт чего счёт отличается от котировки.

Налоги: справочник ставок с признаком применимости (внутренний рейс / международный /
экспорт услуг). Прототип не претендует на юридическую корректность — на экране настройки
ставок стоит соответствующая плашка, и это записано в `docs/GAPS.md`.

### 7.3 Расчёты с поставщиками `[ТЗ 3.4.2]`

- Заявка на оплату формируется автоматически при переходе услуги в «Выполнена»,
  группировка по поставщику и периоду настраивается (по услуге / по рейсу / по неделе).
- Срок оплаты = дата выполнения + отсрочка из контракта; светофор просрочки.
- **Сверка**: загрузка счёта поставщика (CSV/XLSX по шаблону из системы либо ручной
  ввод строк) → автоматическое сопоставление с заявками по ключу
  `поставщик + аэропорт + дата + услуга` → таблица расхождений трёх типов:
  цена отличается, количество отличается, позиция отсутствует с одной из сторон.
  По каждому расхождению — действие: принять счёт поставщика, оставить свою сумму
  и сформировать претензию, пометить на разбор. Все действия в аудит.

### 7.4 Маржинальность рейса `[ТЗ 3.4.3]`

Панель на вкладке «Финансы» и колонка в таблице расписания:
доход (по ценам клиента) — расход (по закупочным ценам) = маржа, в валюте рейса и процентах.
Состояние расчёта помечается: `plan` (по заказанным), `fact` (по выполненным),
`mixed` — если рейс ещё в работе, с явной подписью, какая часть плановая.
Все суммы приводятся к валюте рейса по зафиксированному курсу, курс показывается рядом.

Порог низкой маржи задаётся в настройках; при его нарушении — предупреждение в карточке
и действие «Подобрать более дешёвого поставщика», открывающее сравнение кандидатов (§ 6.2)
с расчётом, как изменится маржа при замене.

## 8. Модуль «Коммуникации» `[ТЗ 3.5]`

### 8.1 Внутренние уведомления `[ТЗ 3.5.1]`

Колокольчик в шапке, центр уведомлений, фильтр по типу и прочитанности.
События: смена статуса рейса, подтверждение или отказ поставщика, приближение дедлайна
(вылет, лидтайм заказа, закрытие документов), нарушение SLA, истечение контракта,
просрочка оплаты, низкая маржа.
Настройки подписки на события — по роли и по пользователю.

### 8.2 Исходящие `[ТЗ 3.5.2]`

Единая очередь исходящих сообщений. Каждое сообщение хранится целиком: канал
(e-mail / MAX / портал), получатель, тема, тело по шаблону с подставленными данными,
вложения (PDF котировки, счёта, заявки). Статусы: в очереди → отправлено → доставлено →
ошибка, с числом попыток и текстом ошибки.

Отправка идёт через адаптер канала (`INTEGRATIONS.md § 3.1, 3.2`):
в режиме `live` — настоящий SMTP или Bot API, в режиме `stub` — запись переводится
в статус «отправлено (заглушка)» без внешнего вызова, и её можно открыть и выгрузить
как `.eml`. Экран один и тот же в обоих режимах, отличается только бейдж канала.

Шаблоны редактируются на `/communications/templates`: переменные вида `{{flight.number}}`,
предпросмотр на выбранном рейсе, версии ru/en (язык письма выбирается по локали получателя).

Обязательный набор шаблонов: подтверждение рейса клиенту, изменение расписания,
отмена рейса, котировка, счёт, закрывающие документы, заявка поставщику, изменение заявки,
отмена заявки, напоминание о сроке исполнения, уведомление об истечении контракта,
претензия по расхождению в сверке.

### 8.3 Входящие

Лента внешних событий: подтверждения и отказы поставщиков, счета поставщиков.
Источники в порядке приоритета: портал поставщика, разбор входящей почты
(`INTEGRATIONS.md § 3.3`), генератор демо-событий на стенде. Каждая запись связана
с заявкой; действие «Применить» меняет её статус. Неопознанные входящие попадают
в очередь ручного разбора — это штатный сценарий, а не ошибка.

### 8.4 Портал клиента `[ТЗ 3.5.3]`

Отдельный лейаут, урезанная навигация: мои рейсы (список и календарь), создание заявки
на рейс (в том числе из своего шаблона), статусы заказанных услуг по рейсу без цен
поставщиков, история заказов, финансовые документы (котировки и счета) с выгрузкой PDF,
профиль и контакты.
Изоляция данных обеспечивается на сервере фильтрацией выборки: запрос чужого рейса
возвращает 404, а не 403 — факт существования чужого рейса не раскрывается.

### 8.5 Портал поставщика `[ТЗ 4.3]`

Входящие заявки с фильтром «требуют ответа», подтверждение или отказ с причиной,
отметка «в процессе» и «выполнена» с указанием фактического времени, загрузка акта,
просмотр своих показателей (доля подтверждений в срок, нарушения SLA, рейтинг),
свои заявки на оплату и их статусы.

### 8.6 Маркировка демонстрационного режима

При `DEMO_DATA=true` (**и только при нём** — см. ADR-008: режимы подключений
на маркировку документов не влияют, иначе боевые счета клиентам получили бы
водяной знак `DEMO` навсегда):

- в шапке веб-клиента и мобильного приложения — бейдж `ДЕМО-СТЕНД`;
- на всех выгружаемых PDF — водяной знак `DEMO`, в XLSX/CSV/XML — первая строка
  `DEMO DATA — NOT FOR OPERATIONAL USE`;
- в исходящих сообщениях режима `stub` — префикс `[DEMO]` в теме;
- на `/admin/integrations` — таблица подключений с фактическим режимом каждого.

В боевом режиме маркировка отсутствует. Управление маркировкой — только через переменные
окружения, отключить её из интерфейса нельзя.

## 9. Модуль «Отчётность и аналитика» `[ТЗ 3.6]`

### 9.1 Стандартные отчёты `[ТЗ 3.6.1]`

Единый построитель: выбор отчёта → параметры (период, клиент, поставщик, аэропорт,
категория услуг, валюта представления) → таблица + график → экспорт.

Обязательный набор:
1. Рейсы за период (сутки / неделя / месяц) с группировкой по клиенту, борту, аэропорту.
2. Оказанные услуги с группировкой по категории и поставщику.
3. Финансовый: доходы, расходы, маржа — по рейсам, клиентам, периодам.
4. Поставщики: объём заказов, доля подтверждений в срок, нарушения SLA, расхождения в сверке.
5. Дебиторская и кредиторская задолженность с разбивкой по срокам (0–30, 31–60, 60+).
6. Реестр нарушений SLA.
7. Журнал изменений рейсов за период (выгрузка из аудита).

### 9.2 Дашборды `[ТЗ 3.6.2]`

**Диспетчер**: рейсы сегодня по статусам, ближайшие вылеты с обратным отсчётом,
неподтверждённые заявки с просроченным лидтаймом, нарушения SLA за сутки, борта в AOG,
конфликты расписания.

**Руководитель**: количество рейсов и динамика, маржа в абсолюте и процентах по периодам,
топ клиентов по выручке и по марже, топ поставщиков по обороту, средняя маржа по категориям
услуг, доля рейсов с маржой ниже порога, загрузка парка ВС.

Виджеты настраиваются: добавление, удаление, перетаскивание, размер; раскладка сохраняется
на пользователя `[ТЗ 3.6.2]`.

### 9.3 Экспорт `[ТЗ 3.6.3]`

PDF, XLSX, CSV, XML. Формирование — на сервере (`BACKEND.md § 8`), чтобы выгрузка больших
отчётов не зависела от браузера и чтобы файл можно было приложить к письму. Схема XML
описывается в `docs/DECISIONS.md`. Маркировка DEMO — по правилам § 8.6.

«Отправка по расписанию» — подписка (получатели, периодичность, время, формат), задача
Celery beat формирует отчёт и ставит сообщение в исходящие.

## 10. Технические разделы `[ТЗ 4]`

### 10.1 Архитектура `[ТЗ 4.1]`

Трёхзвенная: PostgreSQL → серверное приложение (Django + DRF, Celery для фоновых задач) →
клиенты. Подробно — `BACKEND.md`, развёртывание — `INFRA.md`.

Клиенты:
- **Веб-приложение** — основной интерфейс, все роли и оба портала.
- **Мобильное приложение** — React Native (iOS/Android), для диспетчеров и поставщиков,
  с офлайн-режимом. Подробно — `MOBILE.md`.
- **PWA** — веб-клиент устанавливается на домашний экран, как резервный канал для ролей,
  которым не нужна нативная сборка.

Развёртывание `[ТЗ 4.1]`: один и тот же набор образов работает и как SaaS (сервер
исполнителя, изоляция клиентов по `client_id` на уровне выборки), и как on-premise
(инсталляция на инфраструктуре заказчика). Отличие — только конфигурация.

СУБД — PostgreSQL 16. Поддержка MSSQL из п. 4.1 оригинального ТЗ **не реализуется**:
две СУБД удваивают миграции и тесты без выгоды на заявленных нагрузках. Решение
зафиксировано в `docs/DECISIONS.md` и подлежит согласованию с заказчиком; при отказе
согласовать — переход на C#/.NET, что меняет стек целиком.

### 10.2 REST API `[ТЗ 4.2]`

`openapi.yaml` — **контракт, согласованный до написания кода**. Сервер реализует его,
клиенты генерируют типы из него, контрактные тесты проверяют соответствие обеих сторон
(`TESTING.md § 4`). Схема также публикуется сервером через drf-spectacular; расхождение
между файлом контракта и сгенерированной схемой — ошибка сборки.

Базовый путь `/api/v1`. Аутентификация — JWT (access 15 мин, refresh 7 дней) либо OIDC
при подключении LDAP/AD. Формат ответа списка:
`{ data: T[], meta: { total, page, perPage } }`, ошибки:
`{ error: { code, message, details? } }`.

Ресурсы:

### 10.3 Безопасность `[ТЗ 4.3]`

Реализуется полностью на сервере: ролевая модель с проверкой в каждом эндпоинте,
фильтрация выборки по арендатору для ролей «Клиент» и «Поставщик», TOTP-двухфакторная
аутентификация (`pyotp`, приложение-аутентификатор, резервные коды), политика паролей,
блокировка после N неудачных попыток, журнал аудита с неизменяемыми записями.

LDAP/Active Directory — адаптер с режимами `live` и `stub` (`INTEGRATIONS.md § 4.1`).
Для разработки и демонстрации поднимается собственный каталог в контейнере, так что
механизм проверяется по-настоящему ещё до получения доступа к домену заказчика.

Обязательный минимум фиксируемых событий `[ТЗ 4.3]`: создание и изменение рейса, смена
статуса рейса и услуги, назначение и замена поставщика, изменение тарифа, выставление
и аннулирование документа, решение по расхождению в сверке, вход, выход и смена роли,
изменение прав, экспорт персональных данных, любое обращение к данным другого арендатора.

Персональные данные `[152-ФЗ]`: экипажи и пассажиры — персональные данные. Реализуются
разграничение доступа, журналирование обращений, шифрование резервных копий, срок хранения
и процедура удаления. Классификация ИСПДн и аттестация — вне объёма, вопрос вынесен
в `GAPS.md`.

### 10.4 Производительность и надёжность `[ТЗ 4.4]`

Нормативы проверяются нагрузочными испытаниями (`TESTING.md § 5`), а не декларацией:

| Показатель ТЗ | Норматив | Как проверяется |
|---|---|---|
| Одновременных пользователей | 50 | k6, профиль 50 VU, 15 мин |
| Открытие карточки рейса | ≤ 2 с | p95 в отчёте k6 |
| Расчёт маржинальности | ≤ 5 с | p95 в отчёте k6 |
| Восстановление после сбоя | ≤ 30 мин | учебное восстановление из копии с хронометражом |
| Резервное копирование | ежедневно, 30 дней | расписание + журнал заданий + акт восстановления |

Серверные метрики отдаются в Prometheus, дашборд в Grafana, ошибки — в Sentry.
Экран `/admin/performance` показывает фактические перцентили за период, а не синтетику.

### 10.5 Мультиязычность и время `[ТЗ 4.5]`

Полный ru/en для интерфейса, справочников (наименования услуг, категорий, статусов,
причин) и шаблонов сообщений. Переключатель в шапке, выбор сохраняется на пользователя.
Проверка: ни одного «хардкода» русской строки в компонентах, все через `t()`.

Время: хранение UTC, отображение по переключателю UTC / локальное время аэропорта /
время пользователя. Подпись зоны обязательна всегда.

| Пользователи | 8 (по одному на роль + 2 диспетчера) | генератор |

Обязательные «интересные» случаи, иначе демонстрация плоская: рейс с отказом поставщика
и переназначением, рейс с нарушением SLA, рейс с отрицательной маржой, борт в AOG,
счёт с тремя типами расхождений, истекающий контракт, конфликт в расписании,
рейс в валюте, отличной от валюты поставщика.

Все сгенерированные записи получают `is_demo = true`; записи аудита от генератора —
`source = 'seed'` и автора `System (демо-генератор)`, они визуально отличаются в журнале
и не выдаются за действия людей. Наименования клиентов и поставщиков вымышлены; реальными
остаются только общедоступные справочные данные (аэропорты, типы ВС, коды валют).

Команда `seed_demo --purge` очищает демонстрационные записи, не трогая настоящие:
это делает возможным использование одной инсталляции сначала для показа, потом для работы.

## 12. Тестирование

Подробно — `TESTING.md`. Минимум, без которого веха не закрывается:

- **Юнит-тесты (сервер)**: арифметика денег и округления, конвертация валют и фиксация
  курса, разрешение конфликтов тарифных правил, маржа во всех трёх режимах, переходы обоих
  автоматов включая запрещённые, рейтинг поставщика, алгоритм сверки, SLA, нумерация
  документов без дыр при параллельной выдаче.
- **Контрактные тесты**: схема сервера совпадает с `openapi.yaml`; фаззинг эндпоинтов.
- **Интеграционные тесты адаптеров**: каждый адаптер проверяется в режимах `live` (против
  записанных ответов) и `stub`.
- **E2E (Playwright)**: сквозной сценарий ниже.
- **Нагрузочные (k6)**: нормативы § 10.4.

Сквозной сценарий: создать рейс → заказать три услуги у разных поставщиков →
получить отказ по одной и переназначить → подтвердить остальные в портале поставщика →
выставить котировку → провести рейс через все статусы → выставить счёт по факту →
сформировать заявки на оплату → загрузить счёт поставщика с расхождением → разобрать
расхождение → проверить маржу, аудит и содержимое исходящих.

## 13. Приёмка

Система принята, когда:

1. `docs/TRACEABILITY.md` заполнена по всем пунктам разделов 3 и 4 оригинального ТЗ
   со статусом: реализовано / реализовано с адаптером в режиме `stub` (с указанием,
   что требуется от заказчика для перевода в `live`) / не реализовано по согласованию.
   Пустых статусов нет.
2. Сквозной сценарий § 12 проходит в CI на чистой базе.
3. Протокол нагрузочных испытаний подтверждает нормативы § 10.4.
4. Проведено учебное восстановление из резервной копии с хронометражом, составлен акт.
5. Комплект документации из раздела 6 оригинального ТЗ передан: руководство
   администратора, руководство пользователя, регламент эксплуатации.
6. README и `INTEGRATIONS.md` честно отражают фактическое состояние подключений.
