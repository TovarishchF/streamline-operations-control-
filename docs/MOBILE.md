# MOBILE.md — мобильные приложения `[ТЗ 4.1, этап 4]`

---

## 1. Назначение

Два профиля в одном приложении, разделяются по роли после входа:

**Диспетчер** — контроль в пути, а не полноценная работа. Расписание на сегодня и завтра,
карточка рейса, смена статуса, подтверждение и отклонение услуг, звонок поставщику
в одно касание, уведомления.

**Поставщик** — основной рабочий инструмент. Входящие заявки, подтверждение и отказ,
отметка начала и завершения работ с фактическим временем, фотография акта.

Финансовый блок, тарифы и отчёты в мобильное приложение не выносятся: на экране телефона
они нечитаемы, а ошибочное действие в биллинге дороже удобства.

## 2. Стек

| Слой | Выбор |
|---|---|
| Фреймворк | React Native через Expo SDK 52, TypeScript |
| Сборка | EAS Build, профили `development`, `preview`, `production` |
| Навигация | Expo Router |
| Состояние сервера | TanStack Query с персистентным кэшем |
| Локальное хранилище | `expo-sqlite` — кэш и очередь офлайн-операций |
| Защищённое хранилище | `expo-secure-store` — токены |
| Уведомления | `expo-notifications` (FCM + APNs) |
| Типы API | `openapi-typescript`, генерация из `openapi.yaml` — общий контракт с вебом |
| Даты | `dayjs` с теми же плагинами, что на вебе |
| Камера | `expo-camera`, `expo-image-picker` для актов |
| Тесты | Jest + React Native Testing Library, Maestro для e2e |

Доменные расчёты на мобильном **не дублируются**: цены, маржа и статусы приходят
с сервера. Клиент отображает и отправляет команды, не считает.

## 3. Офлайн-режим

Требование не из ТЗ, но без него приложение бесполезно: перрон и ангар — это места
с плохой связью. Пункт внесён в `GAPS.md` как дополнение к ТЗ 4.1.

**Чтение**: список рейсов на ±2 суток, связанные заявки, справочники и контакты
кэшируются в SQLite при каждом успешном запросе. Офлайн показываются кэшированные данные
с отметкой времени последнего обновления.

**Запись**: операции складываются в локальную очередь с `idempotency_key` и отправляются
при появлении связи. Пользователь видит их состояние: отправлено, ожидает, ошибка.

**Конфликты**: сервер — источник истины. При расхождении локальная операция отклоняется
с понятным сообщением («статус уже изменён диспетчером 12:40Z»), данные обновляются.
Молчаливой перезаписи не происходит.

Ограничение офлайна: новые рейсы и документы офлайн не создаются. Офлайн доступны только
операции над уже известными объектами.

## 4. Push-уведомления

События: новая заявка поставщику, приближение дедлайна подтверждения, отказ поставщика,
изменение рейса, нарушение SLA, назначение на рейс.

Тихие часы и настройка подписок — в профиле. Нажатие на уведомление открывает нужный экран
через deep link.

**Нужно от заказчика**: учётные записи Apple Developer (99 $/год) и Google Play
(25 $ однократно), доступ к Firebase для FCM. Без них сборки остаются внутренними
(TestFlight и APK), что допустимо для приёмки, но не для раздачи поставщикам.

---

## 5. Экраны

**Общие**: вход с биометрией после первой авторизации, выбор языка, офлайн-индикатор
в шапке, бейдж `ДЕМО-СТЕНД` при работе против демонстрационного сервера.

**Диспетчер**
- Сегодня: лента рейсов по времени, цвет статуса, счётчик неподтверждённых услуг
- Карточка рейса: свёрнутая версия веб-карточки, доступные переходы статуса кнопками
- Услуги рейса: список с таймерами SLA, действия
- Уведомления
- Поиск по номеру рейса, борту, клиенту

**Поставщик**
- Требуют ответа: заявки с обратным отсчётом до дедлайна
- Карточка заявки: что, где, когда, контакт диспетчера, кнопки «Подтвердить» / «Отказать»
- В работе: отметка начала и завершения, ввод фактического времени, фото акта
- История и показатели
- Мои заявки на оплату

---

## 6. Сборка и публикация

```bash
eas build --profile preview --platform android    # APK для раздачи
eas build --profile production --platform ios     # TestFlight
eas submit --platform android                     # Google Play
```

Артефакты сборок сохраняются с указанием версии, коммита и даты. Версионирование:
`major.minor.patch` синхронно с сервером по мажорной версии API.

Для приёмки достаточно: подписанный APK и сборка в TestFlight с датой и контрольной суммой.

---

## 7. Что проверяется при приёмке

- [ ] Приложение устанавливается на физическое устройство Android и iOS
- [ ] Вход по учётной записи диспетчера и поставщика, роли дают разные экраны
- [ ] В авиарежиме доступны кэшированные рейсы, видна отметка времени обновления
- [ ] Подтверждение заявки офлайн уходит в очередь и отправляется при появлении связи
- [ ] Конфликтная операция отклоняется с понятным сообщением, данные обновляются
- [ ] Push приходит на оба типа устройств и открывает нужный экран
- [ ] Фотография акта загружается и видна в веб-интерфейсе
- [ ] Поставщик не видит ни закупочных цен других поставщиков, ни данных чужих заявок
