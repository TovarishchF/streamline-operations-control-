# INTEGRATIONS.md — реестр внешних подключений

Главный документ для согласования с заказчиком. Отвечает на три вопроса по каждому
внешнему источнику: что это даёт, что нужно получить, как система работает до получения.
Практическая инструкция по включению и проверке — `CONNECTING.md`.

---

## 1. Принцип: адаптер настоящей системы, заглушек нет

Каждое подключение — отдельный пакет в `backend/integrations/<code>/`:

```
integrations/fx/
├── base.py          # Protocol: интерфейс, который видит доменный код
└── live.py          # адаптер настоящей системы
integrations/tests/
└── fixtures/        # записанные ответы систем для тестов
```

Доменный код **никогда** не импортирует адаптер напрямую — только `get_provider("FX")`.

Заглушек нет (ADR-039). Подключение работает, если для него написан адаптер и его код
перечислен в `INTEGRATIONS_ENABLED`. Иначе система к нему не обращается, а функции,
которые на нём держатся, недоступны: придуманные данные не выдаются за ответ внешней
системы. Что делает система без каждого подключения — строка «Без подключения»
в таблицах ниже.

Тесты в сеть не ходят: адаптер проверяется против записанного ответа системы,
а тест, которому нужен канал, подставляет его сам.

## 2. Справочные данные

### 2.1 Курсы валют `[ТЗ 3.4.1]` · код `FX`

| | |
|---|---|
| Что даёт | Курсы USD/EUR/RUB на дату для расчёта маржи и документов |
| Провайдер | ЦБ РФ, `https://www.cbr.ru/scripts/XML_daily.asp?date_req=DD/MM/YYYY` |
| Резервный | ECB Statistical Data Warehouse |
| Доступ | Открытый, ключ не нужен, регистрация не нужна |
| **Нужно от заказчика** | Только решение: какой источник считать официальным для договоров |
| Без подключения | Новых курсов нет; документы считаются по последнему сохранённому курсу с предупреждением |
| Адаптер | Написан, включён по умолчанию |

Курс запрашивается фоновой задачей раз в сутки и **сохраняется в базу**. Документы
ссылаются на сохранённую запись, а не на провайдера: при недоступности источника
система работает на последнем известном курсе и выводит предупреждение.

### 2.2 Погода METAR/TAF `[ТЗ 3.2.1, противообледенительная обработка]` · код `WX`

| | |
|---|---|
| Что даёт | Температура, осадки, видимость в аэропорту — триггер для противообледенительной обработки |
| Провайдер | Aviation Weather Center (NOAA), `https://aviationweather.gov/api/data/metar` |
| Резервный | CheckWX API — требует бесплатной регистрации и ключа |
| Доступ | Открытый, без ключа |
| **Нужно от заказчика** | Ничего |
| Без подключения | Погоды в системе нет; решение об обработке принимает командир ВС (ADR-029) |
| Адаптер | Не написан, 4–8 часов |

### 2.3 Данные о движении ВС `[ТЗ 3.1.2, автопереход «В полёте»]` · код `TRACK`

| | |
|---|---|
| Что даёт | Фактическое время вылета и прилёта для автоматической смены статуса |
| Провайдер | OpenSky Network — бесплатный тариф, аутентификация OAuth2 client credentials |
| Платные | FlightAware AeroAPI, Flightradar24 Business — покрытие и надёжность выше |
| Доступ | OpenSky: бесплатная регистрация. Остальные: договор и оплата |
| **Нужно от заказчика** | Решение о бюджете. OpenSky не покрывает всю бизнес-авиацию и часть бортов не отдаёт вовсе |
| Без подключения | Статусы «В полёте» и «Прибыл» сменяются по плановому времени, фактическое время вносит диспетчер |
| Адаптер | Не написан, 8–16 часов на OpenSky, аналогично на AeroAPI |

Важно: и после подключения возможность ручного ввода фактического времени остаётся —
это не резервный механизм, а основной для бортов без покрытия.

### 2.4 Справочник аэропортов · код `APT`

| | |
|---|---|
| Что даёт | ICAO/IATA, координаты, часовые пояса, страна — основа расчёта маршрута и локального времени |
| Источник | OurAirports, CSV, общественное достояние |
| Часовые пояса | IANA tzdb, встроена в систему |
| Доступ | Свободный |
| **Нужно от заказчика** | Ничего для базового справочника. Для данных по FBO, перронам и рабочим часам служб нужен коммерческий источник (AC-U-KWIK, FBO Directory) либо ручное ведение |
| Без подключения | Не требуется: справочник загружается один раз (`make seed-reference`) и хранится в базе |

Данные по FBO ведутся вручную в реестре поставщиков — это штатное решение,
а не временная мера.

## 3. Каналы обмена сообщениями

### 3.1 Электронная почта, исходящая `[ТЗ 3.5.2]` · код `SMTP`

| | |
|---|---|
| Что даёт | Отправка заявок поставщикам, уведомлений и документов клиентам |
| Провайдер | Любой SMTP: почтовый сервер заказчика либо транзакционный сервис |
| **Нужно от заказчика** | Адрес сервера, порт, учётные данные, адрес отправителя. Настройка SPF, DKIM и DMARC на домене — иначе письма уйдут в спам |
| В разработке | Mailpit в контейнере: письма реально отправляются и видны в веб-интерфейсе, наружу не уходят |
| Без подключения | Письма не уходят: сообщение сразу получает ошибку «подключение не включено» и ждёт повторной отправки |
| Адаптер | Написан, включён по умолчанию; для боя нужны настройки сервера заказчика |

### 3.2 Корпоративный мессенджер MAX `[ТЗ 3.5.1]` · код `MSGR`

| | |
|---|---|
| Что даёт | Внутренние уведомления диспетчерам |
| **Открытый вопрос** | Требуется подтвердить наличие Bot API, лимиты и условия использования в корпоративном контуре. До подтверждения считать канал неподтверждённым |
| **Нужно от заказчика** | Документация API, токен бота, идентификаторы чатов. Либо решение об альтернативе |
| Резервный вариант | Telegram Bot API либо e-mail — реализуются тем же адаптером |
| Без подключения | Канал недоступен: сообщение в мессенджер сразу получает ошибку |
| Адаптер | Не написан, 8–16 часов после получения документации |

Адаптер канала пишется универсальным: `send(channel, recipient, message)`.
Смена мессенджера не затрагивает доменный код.

### 3.3 Разбор входящей почты `[ТЗ 3.2.2, подтверждения поставщиков]` · код `MAILBOT`

| | |
|---|---|
| Что даёт | Автоматический приём подтверждений и счетов от поставщиков, работающих по почте |
| Провайдер | IMAP-ящик заказчика |
| **Нужно от заказчика** | Выделенный ящик (например `ops@`), доступ по IMAP, согласие на автоматическую обработку |
| Реализация | Разбор темы и тела по правилам, извлечение номера заявки, распознавание вложений; неопознанное — в очередь ручного разбора |
| Без подключения | «Входящие» не пополняются; подтверждения вносит диспетчер или поставщик в портале |
| Адаптер | Не написан, 40–60 часов — это отдельный модуль, а не подключение. Разбор писем и экран «Входящие» готовы |

Реалистичная оценка: полностью автоматического разбора не будет. Цель — снять 60–70%
рутины, остальное остаётся диспетчеру. Закладывать в ожидания заказчика именно так.

## 4. Корпоративные системы

### 4.1 LDAP / Active Directory `[ТЗ 4.3]` · код `LDAP`

| | |
|---|---|
| Что даёт | Единый вход сотрудников по доменной учётной записи |
| **Нужно от заказчика** | Адрес контроллера домена, base DN, сервисная учётная запись для чтения, сетевой доступ, карта соответствия групп AD ролям системы |
| Без подключения | Вход только локальными учётными записями. Для разработки адаптера в dev есть OpenLDAP в контейнере |
| Адаптер | Не написан, 8–16 часов |

Локальные учётные записи остаются всегда: администратор системы должен иметь возможность
войти при недоступности домена.

### 4.2 1С:Бухгалтерия `[ТЗ 4.2]` · код `ONEC`

| | |
|---|---|
| Что даёт | Выгрузка счетов клиентам и заявок на оплату поставщикам, приём сведений об оплатах |
| Механизм | OData-интерфейс 1С (`/odata/standard.odata`) либо обмен файлами в согласованном формате |
| **Нужно от заказчика** | Версия и конфигурация 1С; адрес публикации веб-сервиса; учётная запись с правами; **согласованный перечень сопоставляемых реквизитов** (контрагенты, договоры, номенклатура, статьи затрат); контакт ответственного за 1С |
| Разработка | Учебная версия 1С доступна бесплатно — адаптер пишется и тестируется против неё |
| Без подключения | Обмена с 1С нет; документы выгружаются файлами PDF и XLSX |
| Адаптер | Не написан, 60–100 часов, зависит от состояния конфигурации заказчика |

Главный риск проекта после почтового робота. Сроки без осмотра конфигурации оценке
не поддаются, и это должно быть записано в договоре.

### 4.3 Электронный документооборот · код `EDO`

| | |
|---|---|
| Что даёт | Юридически значимая отправка закрывающих документов |
| Провайдер | Диадок, СБИС, Такском |
| **Нужно от заказчика** | Договор с оператором, сертификат электронной подписи, доступ к API, согласие контрагентов на ЭДО |
| В ТЗ | Отсутствует. Внесено в `GAPS.md`: без ЭДО документы всё равно уходят в ручной контур |
| Без подключения | Документы отправляются вне системы |
| Адаптер | Не написан, 40–60 часов после получения доступа |

### 4.4 Системы бизнес-аналитики `[ТЗ 4.2]` · код `BI`

| | |
|---|---|
| Что даёт | Подключение Power BI и Tableau к данным системы |
| Реализация | Реплика PostgreSQL только для чтения + отдельная учётная запись + набор представлений с уже посчитанными метриками |
| **Нужно от заказчика** | Список требуемых показателей; кто и с каких адресов подключается |
| Без подключения | Отчёты выгружаются из раздела «Отчёты» |
| Адаптер | Не создан: реплика и представления — после согласования ADR-005 |

Прямой доступ к таблицам системы не предоставляется: только представления.
Требование ТЗ об ODBC/MySQL-драйверах выполняется именно так, и это записано
в `DECISIONS.md`.

## 5. Отраслевые системы: чего не существует

Здесь подключения нет и не будет — не временно, а постоянно, и заказчик должен это понимать.
Система закрывает задачу своими средствами, описанными в каждом пункте.

### 5.1 Слот-координация аэропортов `[ТЗ 4.2]` · код `SLOT`

Публичного API нет. Координированные аэропорты работают через сообщения формата
IATA SSIM (SCR/SIR) по электронной почте либо через веб-кабинеты координаторов.

Реализуется: реестр слотов с ручным вводом, формирование сообщения SCR по шаблону,
разбор ответного сообщения. Это не интеграция, а инструмент подготовки сообщений.

**Нужно от заказчика**: перечень аэропортов, где реально требуется координация,
и образцы переписки.

### 5.2 Системы поставщиков `[ТЗ 4.2]` · код `VENDOR_API`

У подавляющего большинства FBO, топливных операторов и кейтеринга публичного API нет.
Основные каналы остаются: портал поставщика в самой системе и почтовый робот (§ 3.3).

Реализуется универсальный адаптер: если у конкретного поставщика API появится, к нему
пишется реализация без изменения доменного кода. В карточке поставщика есть поле
«способ обмена»: портал / почта / API.

**Нужно от заказчика**: список поставщиков, у которых обмен уже как-то автоматизирован.

### 5.3 IATA SIS / ISS `[ТЗ 4.2, «IATA BDG»]` · код `IATA`

Аббревиатура BDG в оригинальном ТЗ требует уточнения — отраслевой стандарт межрасчётов
называется IATA SIS (Simplified Invoicing and Settlement), формат IS-XML.

Участие требует членства в IATA и сертификации, это отдельный проект со своим бюджетом
и сроком. В рамках настоящего договора реализуется только **выгрузка в формате IS-XML**
как файл — это закрывает «стандартизацию биллинговых данных» и не требует членства.

**Нужно от заказчика**: подтверждение, что имелось в виду именно SIS, и решение о том,
нужна ли отправка или достаточно формата выгрузки.

## 7. Журнал обменов

Каждый вызов внешней системы пишется в таблицу `integration_log`: код подключения,
операция, эндпоинт, время, длительность, статус, код ответа, размер ответа, идентификатор
связанной сущности. Тела запросов и ответов хранятся 30 дней, реквизиты доступа
и персональные данные в журнал не попадают.

Экран `/admin/integrations`: работающие подключения, доступность по последнему обмену,
время последней проверки и последнего успешного обмена, кнопка «Проверить», журнал
обменов. Записи, сделанные заглушками до ADR-039, хранятся с `mode=stub` и не показываются.

Этот журнал — доказательная база при разборе спорных ситуаций с поставщиками и главный
инструмент отладки подключения.
