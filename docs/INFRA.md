# INFRA.md — инфраструктура и развёртывание

---

## 1. Состав среды

| Сервис | Образ | Назначение |
|---|---|---|
| `db` | postgres:16 | основная база |
| `db-replica` | postgres:16 | реплика только для чтения: отчёты и BI |
| `redis` | redis:7 | кэш, брокер Celery, идемпотентность |
| `api` | собственный | Django + Gunicorn |
| `worker` | собственный | Celery worker |
| `beat` | собственный | Celery beat |
| `web` | nginx | статика веб-клиента и прокси на `api` |
| `minio` | minio | файловое хранилище (только on-premise) |
| `mailpit` | mailpit | перехват почты (только dev и стенд) |
| `openldap` | osixia/openldap | тестовый каталог (только dev и стенд) |
| `prometheus`, `grafana`, `loki` | — | метрики и логи |

Один `docker-compose.yml` с профилями: `dev`, `demo`, `prod`. Разница — переменные
окружения и набор вспомогательных сервисов, а не разные файлы конфигурации.

---

## 2. Окружения

| Окружение | Назначение | Данные | Интеграции |
|---|---|---|---|
| `dev` | разработка | `seed_demo` | все `stub`, почта в Mailpit |
| `demo` | показ заказчику | `seed_demo` | все `stub`, маркировка `ДЕМО-СТЕНД` |
| `stage` | приёмочные испытания | обезличенная копия рабочих | частично `live` |
| `prod` | эксплуатация | рабочие | `live` |

Демонстрационный стенд — это `prod`-сборка с `DEMO_DATA=true` и заглушками.
Отдельного «демо-кода» не существует; ветвление только по конфигурации.

## 3. Переменные окружения

```bash
# Основное
DJANGO_SETTINGS_MODULE=config.settings.prod
SECRET_KEY=
ALLOWED_HOSTS=

REPLICA_DATABASE_URL=postgres://...

# Режим демонстрации

# Интеграции — по умолчанию stub (см. INTEGRATIONS.md)
INTEGRATION_FX_MODE=stub
INTEGRATION_WX_MODE=stub
INTEGRATION_TRACK_MODE=stub
INTEGRATION_SMTP_MODE=stub
INTEGRATION_MSGR_MODE=stub
INTEGRATION_MAILBOT_MODE=stub
INTEGRATION_LDAP_MODE=stub
INTEGRATION_ONEC_MODE=stub
INTEGRATION_EDO_MODE=stub

# Учётные данные подключений — заполняются при переводе в live
ONEC_ODATA_URL= ONEC_USER= ONEC_PASSWORD=
```

Секреты не попадают в репозиторий. Для on-premise — файл `.env` с правами 600,
для облака — менеджер секретов провайдера. В репозитории только `.env.example`
со всеми ключами и пустыми значениями.

## 4. Резервное копирование `[ТЗ 4.4]`

- **pgBackRest**: полная копия еженедельно, инкрементальная ежедневно, архивация WAL
  непрерывно. Это даёт восстановление на произвольный момент времени, а не только
  на вчерашнюю ночь — иначе при сбое теряются сутки финансовых данных.
- Хранение 30 дней, согласно ТЗ.
- Копии шифруются, хранятся вне основного сервера.
- Ежедневная автоматическая проверка целостности последней копии.
- Ежемесячное учебное восстановление с хронометражом (`TESTING.md § 6`).
- Файловое хранилище копируется отдельно, версионирование включено.

Без проверки восстановления резервное копирование считается несуществующим.
Это правило записывается в регламент эксплуатации.

## 5. Наблюдаемость

- Метрики: `django-prometheus`, метрики PostgreSQL и Redis, дашборды в Grafana.
- Логи: структурные JSON, сбор в Loki, срок хранения 90 дней.
- Ошибки: Sentry с привязкой к релизу и коммиту.
- Алерты: недоступность `/health`, доля ошибок 5xx выше 1%, задержка очереди Celery
  больше 5 минут, заполнение диска выше 80%, провал резервного копирования,
  недоступность подключения в режиме `live` дольше 30 минут.

Алерты уходят на почту и в мессенджер дежурного.

## 6. Безопасность развёртывания

- HTTPS обязателен, сертификат Let's Encrypt либо корпоративный, HSTS включён.
- База и Redis не публикуются наружу, доступ только из сети контейнеров.
- Приложение подключается к базе учётной записью без прав `DROP` и без `UPDATE`/`DELETE`
  на таблицу аудита.
- Отдельная учётная запись только для чтения — для BI, с доступом к реплике
  и только к представлениям.
- Резервные копии шифруются.
- Автоматическое обновление базовых образов с пересборкой при выходе исправлений
  безопасности.
- Файлы пользователей проверяются по типу и размеру, отдаются по подписанным ссылкам
  со сроком жизни, а не по прямому пути.

Персональные данные `[152-ФЗ]`: при размещении в облаке сервер должен находиться
на территории РФ. Вопрос классификации ИСПДн и необходимости аттестации вынесен
в `GAPS.md` и требует решения заказчика до ввода в эксплуатацию.

## 7. Целевая конфигурация

Для заявленных 50 пользователей достаточно одного сервера: 4 vCPU, 8 ГБ памяти,
100 ГБ SSD. Реплика и хранилище файлов могут жить на нём же на старте.

Кластеризация PostgreSQL из ТЗ 4.1 при такой нагрузке избыточна; реализуется реплика
с возможностью ручного переключения. Полноценный автоматический отказоустойчивый кластер
(Patroni) выносится в отдельное соглашение, решение фиксируется в `DECISIONS.md`.

## 8. Порядок первого развёртывания

```bash
cp .env.example .env            # заполнить
docker compose --profile prod up -d db redis minio
docker compose run --rm api python manage.py migrate
docker compose run --rm api python manage.py loaddata airports    # справочник аэропортов
docker compose run --rm api python manage.py createsuperuser
docker compose --profile prod up -d
# для демонстрационного стенда:
docker compose run --rm api python manage.py seed_demo --seed 20260912
```

Процедура целиком переносится в руководство администратора и проверяется на чистой
машине перед сдачей: если развернуть по инструкции не получилось, инструкция неверна.
