# BACKEND.md — серверная часть

Реализует доменную модель и формулы из `DOMAIN.md`. При расхождении текстов формул
приоритет у `DOMAIN.md`.

## 2. Структура приложений

```
backend/
├── config/              # settings (base/dev/prod), urls, celery, wsgi/asgi
├── core/                # базовые модели, Money, миграции справочников, утилиты
├── accounts/            # пользователи, роли, права, 2FA, LDAP
├── catalog/             # услуги, атрибуты, цены поставщиков, аэропорты, типы ВС
├── counterparties/      # клиенты, поставщики, контракты, сертификаты, тарифы
├── fleet/               # борта, техсостояние, AOG
├── flights/             # рейсы, шаблоны, автомат рейса, конфликты расписания
├── orders/              # заявки на услуги, автомат заявки, SLA
├── billing/             # котировки, счета, заявки на оплату, сверка, маржа, НДС
├── comms/               # шаблоны, уведомления, исходящие, входящие
├── reports/             # отчёты, дашборды, экспорт
├── integrations/        # адаптеры внешних систем (см. INTEGRATIONS.md)
├── audit/               # журнал аудита
└── demo/                # генератор демонстрационных данных
```

Правило зависимостей: `flights` может импортировать `catalog` и `counterparties`,
обратное запрещено. `billing` зависит от `orders`, обратное запрещено.
Циклические импорты между приложениями — ошибка архитектуры, решается событиями.

## 3. Правила реализации

### 3.1 Сервисный слой

Бизнес-логика живёт в `<app>/services/`, а не во вьюхах, сериализаторах или `Model.save()`.
Вью принимает запрос, валидирует, вызывает сервис, сериализует результат. Сериализатор
не считает деньги и не меняет статусы.

Каждая операция, меняющая данные, — функция вида:

```python
def assign_vendor(*, order: ServiceOrder, vendor: Vendor, actor: User) -> ServiceOrder:
    """ТЗ 3.3.2. Назначает поставщика и фиксирует снимок закупочной цены."""
```

Обязательные признаки: именованные аргументы, явный `actor` для аудита, транзакция,
запись в аудит внутри той же транзакции.

### 3.2 Деньги

Модель хранит пару полей: `<name>_amount` (Decimal 18,4) и `<name>_currency` (CharField 3).
Работа — через `core.money.Money`, конструируемый из пары. Сложение разных валют бросает
исключение. Округление до 2 знаков `ROUND_HALF_UP` — только на итоговых суммах документа,
промежуточные расчёты идут с 4 знаками.

`FloatField` для денег запрещён, проверяется линтером через кастомное правило.

### 3.3 Автоматы

`django-fsm-2`, переходы объявляются декоратором с `source`, `target` и `conditions`.
Guard-функции из `DOMAIN.md § 5` реализуются как отдельные предикаты, покрытые тестами.
Побочные эффекты (аудит, уведомления, пересчёт маржи, создание заявки на оплату)
вызываются в сервисе после успешного перехода, в той же транзакции, кроме отправки
наружу — она уходит в Celery через `transaction.on_commit`.

Прямое присвоение `obj.status = ...` запрещено: поле защищено `protected=True`.

### 3.4 Неизменяемость документов

Выставленные котировки и счета не редактируются. Обеспечивается тремя уровнями:
проверка в сервисе, `CheckConstraint` в базе, отсутствие эндпоинта на изменение.
Правка — только через `void` с выпуском нового документа и ссылкой `voided_by`.

### 3.5 Нумерация документов

Отдельная таблица `DocumentCounter(doc_type, year, last_number)`, выдача номера —
`select_for_update()` внутри транзакции документа. Это даёт сквозную нумерацию без дыр
при параллельной работе. Тест на параллельную выдачу 100 номеров в 10 потоков обязателен.

### 3.6 Снимки

При назначении поставщика закупочная цена **копируется** в заявку, а не связывается
ссылкой на прайс. То же для курса валюты в документе и условий контракта на дату заказа.
Последующее изменение прайса не меняет историю — это проверяется тестом.

### 3.7 Мультиарендность

Одна база, изоляция на уровне выборки. Базовый класс `TenantScopedViewSet` подмешивает
фильтр: для роли `client` — по `client_id` пользователя, для `vendor` — по `vendor_id`.
Обращение к чужой записи даёт 404. Фильтр применяется в `get_queryset()`, а не в проверке
объекта — иначе списочные эндпоинты протекают.

Тест на протечку данных обязателен для каждого эндпоинта, доступного порталам.

### 3.8 Идемпотентность

Заголовок `Idempotency-Key` на всех POST. Ключ и ответ кладутся в Redis на 24 часа.
Фоновые задачи, порождающие сообщения, используют `dedupe_key`
(например `contract_expiry:{id}:30`), уникальный индекс в базе не даёт продублировать.

### 3.9 Аудит

Модель `AuditEntry` по `DOMAIN.md § 8`, только вставка. Удаление и изменение запрещены
правами пользователя базы: приложение подключается учётной записью без `UPDATE`/`DELETE`
на эту таблицу. Diff считается сервисом и хранится как JSONB.

Соответствие один к одному, с поправками на реляционность:

| Тип в DOMAIN.md | Модель | Примечания |

| `Client`, `Vendor`, `VendorContract` | `counterparties.*` | |

| `Flight`, `FlightTemplate` | `flights.*` | `fx_snapshot` — JSONB |
| `ServiceOrder` | `orders.ServiceOrder` | снимки цены — обычные поля |

| `PayableItem`, `VendorInvoice`, `Discrepancy` | `billing.*` | |
| `AuditEntry` | `audit.AuditEntry` | |

очистку демонстрационных записей без затрагивания рабочих.

## 5. Фоновые задачи (Celery Beat)

| Задача | Расписание | Что делает |
|---|---|---|
| `fx.sync_rates` | 06:00 UTC | Запрашивает курсы, сохраняет в базу |
| `flights.auto_depart` | каждую минуту | Переводит рейсы в «В полёте» по данным `TRACK` либо по плановому времени |
| `flights.auto_arrive` | каждую минуту | Аналогично для прилёта |
| `orders.check_sla` | каждые 5 минут | Помечает нарушения, шлёт уведомления |
| `contracts.check_expiry` | 08:00 местного | Уведомления за 30/15/7 дней |
| `billing.check_overdue` | 09:00 | Просроченная дебиторка и кредиторка |
| `billing.check_margin` | при изменении рейса | Предупреждение при марже ниже порога |
| `comms.send_outbox` | каждые 30 секунд | Отправка очереди с повторами и экспоненциальной задержкой |
| `comms.poll_inbox` | каждые 5 минут | Разбор входящей почты (`MAILBOT`) |
| `reports.scheduled` | ежедневно и еженедельно | Формирование и рассылка подписок |
| `integrations.health` | каждые 15 минут | Проверка доступности подключений |
| `db.backup_verify` | ежедневно | Проверка целостности последней копии |

Задачи идемпотентны и переживают повторный запуск. Долгие задачи пишут прогресс.

## 6. Аутентификация и права

- JWT: access 15 мин, refresh 7 дней, ротация refresh, чёрный список при выходе.
- TOTP: `pyotp`, привязка через QR, 10 резервных кодов, обязательна для ролей
  `admin` и `finance`, опциональна для остальных — настраивается.
- LDAP: `django-auth-ldap`, соответствие групп ролям из настроек, локальные учётные
  записи сохраняются как резервный путь.
- Права: класс на каждый эндпоинт, карта `role → permission` в `accounts/permissions.py`,
  один источник истины с фронтендом — генерируется в JSON и отдаётся в `/auth/me`.
- Блокировка после 5 неудачных попыток на 15 минут, событие в аудит.

## 7. Расчёты

Все формулы из `DOMAIN.md § 7` реализуются в `billing/services/` и `counterparties/services/`
как чистые функции, принимающие данные и возвращающие результат, без обращения к базе
внутри. Обращение к базе — на уровень выше. Это делает их тестируемыми и переносимыми.

Маржа рейса считается по запросу и кэшируется в Redis с инвалидацией по событиям
изменения заявок. Норматив 5 секунд из ТЗ 4.4 достигается с большим запасом; кэш нужен
для дашбордов, где маржа считается по сотням рейсов сразу.

## 9. Обработка ошибок и ответы

Единый обработчик исключений DRF, формат `{ error: { code, message, details } }`.
Коды ошибок — перечисление, документируется в OpenAPI. Доменные исключения
(`TransitionNotAllowed`, `ContractExpired`, `PriceNotFound`, `CurrencyMismatch`)
отображаются в HTTP-коды таблицей, а не случайно.

Пользователь всегда получает сообщение, по которому понятно, что делать:
не «ошибка валидации», а «у поставщика X истёк контракт 12.03.2026, выберите другого
или продлите договор».

## 10. Миграция данных

Отдельная команда `import_legacy` для загрузки текущих данных заказчика из Excel и 1С:
режим проверки (что загрузится, какие ошибки), режим загрузки, журнал соответствия
исходных и созданных записей, возможность откатить загрузку целиком.

Без этой команды опытная эксплуатация невозможна, а в оригинальном ТЗ она не упомянута —
пункт внесён в `GAPS.md`.
