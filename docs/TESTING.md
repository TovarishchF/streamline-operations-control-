# TESTING.md — испытания `[ТЗ 4.4, этап 6]`

Документ покрывает и разработческое тестирование, и приёмочные испытания.
Итоговый протокол испытаний собирается из результатов разделов 3–7 и служит основанием
для акта по этапу 6 оригинального ТЗ.

---

## 1. Пирамида

| Уровень | Инструмент | Где | Когда запускается |
|---|---|---|---|
| Юнит | pytest | сервер | каждый коммит |
| Юнит | Vitest | веб, мобильный | каждый коммит |
| Интеграционные | pytest + testcontainers | сервер + реальная PostgreSQL | каждый коммит |
| Контрактные | schemathesis | API против `openapi.yaml` | каждый коммит |
| Адаптеры | pytest + записанные ответы | `integrations/` | каждый коммит |
| E2E | Playwright | веб + сервер | каждый merge в main |
| Мобильные E2E | Maestro | эмулятор | перед сборкой |
| Нагрузочные | k6 | стенд | еженедельно и перед приёмкой |
| Восстановление | скрипт + хронометраж | стенд | ежемесячно и перед приёмкой |

Порог покрытия: 90% для `billing/`, `orders/`, `flights/services/`, `core/money/`.
Для остального — 70%. Порог проверяется в CI, снижение блокирует merge.

## 2. Обязательные юнит-тесты

Список не подлежит сокращению — это места, где ошибка стоит денег заказчика.

**Деньги** (`core/money`): сложение разных валют бросает исключение; округление
на граничных значениях 0.005, 0.015, 2.675; сумма 1000 позиций по 0.005 не расходится
с ожидаемой; конвертация туда-обратно не теряет копейки сверх допустимого.

**Тарифы** (`DOMAIN.md § 7.2`): приоритет правил при пересечении областей действия;
правило с более поздним `valid_from` при равном приоритете; отсутствие правила даёт
наценку по умолчанию; все три способа ценообразования; скидка применяется после наценки.

**Маржа** (`§ 7.3`): три режима расчёта; отрицательная маржа не обнуляется;
нулевая выручка даёт `null` в проценте, а не деление на ноль; мультивалютный рейс.

**Автоматы** (`§ 5`): каждый разрешённый переход; каждый запрещённый переход бросает
исключение; guard «готов к вылету» при неподтверждённой услуге; каскадная отмена заявок
при отмене рейса.

**Снимки**: изменение прайса поставщика после назначения не меняет сумму заявки;
изменение тарифа после выставления документа не меняет документ.

**Нумерация**: 100 документов в 10 параллельных потоках дают сквозную нумерацию без дыр
и без дублей.

**Сверка** (`§ 7.7`): каждый из четырёх типов расхождений; допуск на округление;
строка, попадающая в окно ±1 день.

**Рейтинг и подбор** (`§ 7.4, 7.5`): «недостаточно данных» при менее чем 5 заявках;
изменение порядка кандидатов при смене весов.

**SLA** (`§ 7.6`): нарушение по подтверждению; нарушение по выполнению; расчёт штрафа.

**Изоляция арендаторов**: для каждого эндпоинта портала — запрос чужой записи даёт 404,
списочный запрос не содержит чужих записей.

## 3. Контрактные тесты

Схема, сгенерированная `drf-spectacular`, сравнивается с `openapi.yaml`. Расхождение
останавливает сборку. Это защищает от ситуации, когда сервер и клиенты расходятся молча.

`schemathesis` прогоняет сгенерированные запросы по всем эндпоинтам: проверяются коды
ответов, соответствие схеме, отсутствие 500 на некорректных входных данных.

---

## 4. Тесты адаптеров `[INTEGRATIONS.md]`

Для каждого подключения:
1. Режим `stub` даёт детерминированный ответ нужного формата.
2. Режим `live` тестируется против записанных ответов (`cassettes/`), реальная сеть
   в тестах не используется.
3. Ошибка провайдера обрабатывается: таймаут, 500, некорректный формат, пустой ответ.
4. Доменный код ведёт себя одинаково в обоих режимах — один и тот же тест прогоняется
   дважды с разной конфигурацией.

Пункт 4 — главный: он доказывает, что переход `stub → live` не потребует правок логики.

## 5. Нагрузочные испытания `[ТЗ 4.4]`

Инструмент — k6. Стенд по конфигурации соответствует целевой среде.

### 5.1 Профиль нагрузки

50 виртуальных пользователей, распределение по ролям пропорционально ожидаемому:
30 диспетчеров, 10 финансистов, 5 руководителей, 5 порталов.
Разгон 2 минуты, плато 15 минут, спад 1 минута.

Сценарий диспетчера: открыть расписание → открыть карточку рейса → открыть услуги →
сменить статус заявки → вернуться к расписанию. Паузы 3–10 секунд между действиями.

Отдельный пиковый прогон: 150 пользователей на 5 минут — проверка поведения при
трёхкратном превышении норматива. Деградация допустима, отказ обслуживания — нет.

### 5.2 Пороги

```js
thresholds: {
  'http_req_duration{name:flight_card}': ['p(95)<2000'],   // ТЗ 4.4
  'http_req_duration{name:margin_calc}': ['p(95)<5000'],   // ТЗ 4.4
  'http_req_duration{name:schedule}':    ['p(95)<3000'],
  'http_req_failed':                     ['rate<0.01'],
  'checks':                              ['rate>0.99'],
}
```

Прогон с непройденным порогом — это результат испытания, а не повод его переделать.
В протокол попадает фактическое значение, а не желаемое.

### 5.3 Что фиксируется в протоколе

Конфигурация стенда, объём данных в базе, профиль нагрузки, перцентили по каждому
сценарию, доля ошибок, потребление CPU и памяти сервером и базой, медленные запросы
из `pg_stat_statements`. HTML-отчёт k6 прикладывается как есть.

## 6. Испытание восстановления `[ТЗ 4.4]`

Норматив: восстановление не более 30 минут, копии ежедневно, хранение 30 дней.

Методика:
1. Зафиксировать состояние базы (контрольные суммы по ключевым таблицам).
2. Уничтожить экземпляр базы на стенде.
3. Засечь время. Восстановить из последней копии по инструкции из руководства
   администратора — именно по инструкции, а не по памяти.
4. Остановить время после успешного входа в систему и прохождения проверки `/health`.
5. Сверить контрольные суммы, проверить целостность связей.
6. Отдельно проверить восстановление на точку во времени (PITR) на произвольный момент.

Результат — акт с хронометражом. Если инструкция оказалась неполной, она правится,
и испытание повторяется: это и есть проверка руководства администратора.

## 7. Приёмочные испытания

Оформляются программой и методикой испытаний (ПМИ) по структуре ГОСТ 34.603:
объект испытаний, цели, состав, условия, средства, методика по каждому требованию ТЗ,
критерии оценки.

Каждое функциональное требование разделов 3 и 4 оригинального ТЗ получает строку:
номер пункта, формулировка требования, метод проверки (демонстрация / измерение /
анализ документа), ожидаемый результат, фактический результат, отметка о соответствии.

Строки со статусом «реализовано с адаптером в режиме `stub`» помечаются отдельно
с указанием, что требуется от заказчика для перевода в боевой режим. Это честная
и защитимая формулировка: функция реализована, внешнее подключение не предоставлено.

## 8. CI

GitHub Actions (либо GitLab CI), этапы:

```
lint        → ruff, mypy, eslint, tsc
unit        → pytest, vitest
integration → pytest с PostgreSQL в сервисном контейнере
contract    → сравнение схем + schemathesis
build       → сборка образов, сборка веб-клиента
e2e         → docker compose up + playwright
```

Merge в `main` без зелёного пайплайна невозможен. Ночной прогон дополнительно гоняет
k6 на стенде и публикует отчёт.

Артефакты сохраняются: отчёты покрытия, HTML-отчёты Playwright и k6, образы с тегом
коммита. Эти артефакты — доказательная база выполнения этапа 6, и они машинно
датированы.
